# ZiuroDB — Data Storage & Architecture Guide

This document explains the data storage mechanics, persistence layers, and architectural design of ZiuroDB, covering both the **Backend Schema Intelligence Subsystem** and the **Desktop Application Storage System**.

---

## Part 1: Backend Schema Graphs (`backend/data/schema-graphs/`)

### 1.1 What is stored in `backend/data/schema-graphs`?
The `backend/data/schema-graphs/` directory stores **compressed Knowledge Graph files** (`.graph.gz`) generated by the **ZiuroDB Schema Intelligence Engine**.

Each connected database has a dedicated file named after its connection ID:
```
backend/data/schema-graphs/
├── 65f9a2b8e4b01c2d3e4f5678.graph.gz
├── 65f9a3c9e4b01c2d3e4f5679.graph.gz
└── ...
```

---

### 1.2 Data Flow — Where does the data come from?

```
┌────────────────────────┐
│  Connected Database    │ (PostgreSQL, MySQL, MongoDB, Firebase)
└───────────┬────────────┘
            │ 1. Introspection Scan (Tables, Columns, Indexes, FKs)
            ▼
┌────────────────────────┐
│  ScanOrchestrator      │ (Deep Schema Inspection)
└───────────┬────────────┘
            │ 2. Build Nodes & Edges
            ▼
┌────────────────────────┐
│  KnowledgeGraph        │ (In-Memory Graph Representation)
└───────────┬────────────┘
            │ 3. Semantic Classification & Relationship Inference
            ▼
┌────────────────────────┐
│  GraphSerializer       │ (JSON Serialization)
└───────────┬────────────┘
            │ 4. Gzip Compression (zlib.gzipSync)
            ▼
┌────────────────────────┐
│  FileGraphStorage      │ (Saved to backend/data/schema-graphs/*.graph.gz)
└────────────────────────┘
```

#### Step-by-Step Processing:
1. **Introspection Scan**: When a database connection is scanned (automatically during AI interaction or manually via button), `ScanOrchestrator` uses database drivers (`information_schema` queries for SQL, collection metadata for Mongo) to inspect:
   - Database names and schema namespaces
   - Tables, views, and collections
   - Columns, field data types, nullability, and default values
   - Primary keys, foreign keys, and indexes
2. **Graph Construction**: The `KnowledgeGraph` class constructs a directed graph of nodes (`DATABASE`, `SCHEMA`, `TABLE`, `COLUMN`, `INDEX`, `FOREIGN_KEY`, `MONGO_FIELD`) connected by typed relationship edges.
3. **Semantic Enrichment**:
   - `SemanticClassifier` categorizes business entities (e.g., `user`, `order`, `financial_transaction`).
   - `RelationshipInferrer` automatically detects unconstrained relationships (e.g., matching `user_id` in `orders` to `id` in `users`).
4. **Serialization & Compression**: `GraphSerializer` converts the in-memory graph structure to a structured JSON payload, which `FileGraphStorage` compresses using Gzip (`zlib.gzipSync`) before saving to disk.

---

### 1.3 Why is this data stored?

- ⚡ **AI Prompt Token Optimization (RAG Context)**:
  When Ziuro AI generates SQL/ZQL queries or answers database questions, loading the entire schema into the LLM prompt can consume tens of thousands of tokens. The Schema Intelligence Engine loads this `.graph.gz` file and extracts only the relevant sub-graph using `ContextRetriever`, saving **80–90% of tokens** while improving query accuracy.
- 🩺 **Schema Health Diagnostics**:
  Powers the **Schema Health Score**, orphan table detection, index advice, and wide table warnings without straining your production database.
- 💾 **Fast Cold Restarts**:
  In-memory `GraphCache` falls back to loading `.graph.gz` files on backend restarts, preventing expensive re-scans of production databases.

## Part 2: Desktop App Storage Architecture (Electron)

The **ZiuroDB Desktop Application** uses a **local-first, multi-tiered hybrid storage design**:

```
┌──────────────────────────────────────────────────────────────────┐
│                   ZiuroDB Desktop App Storage                    │
├──────────────────┬─────────────────┬──────────────┬──────────────┤
│  electron-store  │ ~/ZiuroDB/Pool/ │  db-bridge   │ Web Storage  │
│  (Config & Auth) │ (Local Media/   │ (Direct DB   │ (UI State &  │
│                  │  Chunks/Meta)   │  Drivers)    │  Local Cache)│
└──────────────────┴─────────────────┴──────────────┴──────────────┘
```

---

### 2.1 Storage Layers Breakdown

| Storage Layer | Storage Mechanism | Physical Path / Location | Stored Content |
|---|---|---|---|
| **Preferences & Credentials** | `electron-store` | OS AppData Directory<br>• macOS: `~/Library/Application Support/ziurodb/config.json`<br>• Windows: `%APPDATA%\ziurodb\config.json`<br>• Linux: `~/.config/ziurodb/config.json` | Active theme (`dark`, `light`, `dark-gray`), encryption keys, saved database connection profiles, storage node allocations, user session tokens. |
| **Local Storage Pool & Media** | `storage-manager.ts` | Default: `~/ZiuroDB/storage-pool/`<br>• `/chunks/`<br>• `/meta/`<br>• `/media/` | • `chunks/`: Encrypted binary storage chunks for decentralized storage nodes.<br>• `meta/`: Chunk metadata JSON descriptors.<br>• `media/`: Local media assets (images, audio, video) served via built-in local HTTP server. |
| **Direct DB Drivers** | `db-bridge.ts` | Main Process Memory & Filesystem | Native drivers (PostgreSQL `pg`, MySQL `mysql2`, MongoDB driver, Redis, SQLite) execute operations directly from Electron main process. SQLite `.db` files read directly from disk. |
| **UI State & Web Cache** | `localStorage` & `IndexedDB` | Chromium Renderer Process Storage | Sidebar collapse state, active tab selections, ZQL query console draft buffers, cached UI components. |

---

### 2.2 Embedded Local Media HTTP Server

To allow fast, offline preview of binary media assets stored in local storage pools:
- **Port**: `http://localhost:19876`
- **Route**: `GET /media/:assetId/raw`
- **Function**: The main process (`main.ts`) runs an internal Node.js HTTP server with CORS enabled to serve binary data from `~/ZiuroDB/storage-pool/media/` directly to the frontend viewer with zero network overhead.

## Summary Matrix

| Subsystem | Storage Location | Data Format | Purpose |
